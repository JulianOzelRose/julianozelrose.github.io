Reverse Engineering Tomb Raider VI's Compression Algorithm

Reverse Engineering / Compression

Reconstructing a proprietary compression algorithm using decompiled C, x86/x64 assembly, runtime debugging, and differential testing to reproduce the game's output byte-for-byte.

10-04-2026

Introduction

When doing the reverse engineering work to build a savegame editor, you're typically looking in two places: the savegame file itself, and the game's decompilation. You use both to try to understand what the game is doing and how the structs are stored on the savegame. The more dynamic the data is, the more you have to rely on understanding the game's code and how it deserializes the data.

Tomb Raider VI is a difficult program to reverse engineer enough to build a working editor for because it uses a proprietary LZW compression algorithm to compress the savegame buffer. When I started working on it, I began by locating the buffer on the savegame file.

Notice the size parameter, followed by what appears to be padding, followed by the 1F 9D 8C magic header, followed by high-entropy data. This is clearly compressed data. As far as being able to find any meaningful insights from the buffer stored on the file, this was a brick wall.

Finding the Decompression Routine

Fortunately the game shipped with debug symbols, so locating the compression and decompression algorithms was fairly straightforward. The game calls the decompression algorithm Unpack(). It is a proprietary variant of the LZW algorithm.

Since it's proprietary, using a standard LZW library to handle decompression will not work. The only way forward is to reverse engineer the decompression and compression algorithms from scratch. Here is the decompression algorithm as shown in Ghidra's C decompilation:

Reversing Unpack

When recreating Unpack(), I began by identifying the constants and the basic operations in the control flow so I could create a primitive Python script. Below is a table of what the constants seen in the decompilation represent:

Decompiler Variable Meaning Initial Value
uVar12 Next dictionary code 0x100
uVar7 Current code width 9 bits
uVar8 Current code mask 0x1FF

Next is mapping the control flow. The most immediately apparent thing is the 1F 9D 8C magic header validation in the beginning of the function. Then there's the variable-width codes, dictionary growth, literal values, CLEAR codes and dictionary resets, and bitstream alignment.

Understanding this enough to reproduce it took a lot of trial and error. Fortunately, the C pseudocode produced by Ghidra was clean enough to map it into Python. I believe I had a working Python reconstruction of Unpack() within a week.

Testing Unpack

When testing a reverse-engineered function like this, the goal is to produce identical output to what the game/program does. In this case, the game takes a compressed buffer from the savegame file, performs its decompression routine, and then loads the decompressed buffer into memory.

My strategy here was pretty straightforward. I would load a savegame, then dump the decompressed buffer from the game's memory immiedately after loading, then run my Python recreation of Unpack() on the same savegame. I would then use a hex editor to diff the two decompressed buffers and see how my Python recreation had performed.

My first implementation reproduced roughly the first 17% of the decompressed buffer before diverging. Most of the algorithm was already correct, but I had interpreted the post-CLEAR alignment incorrectly. Adjusting this made the Python recreation consistently reproduce the same results as the game did.

As with the decompression algorithm, the first step to recreating it in Python was to try to understand the constants, and then the basic operations in the control flow. Next is mapping the control flow. The general flow of Pack() is that it reads the input buffer, searches the dictionary for matching sequences, then emits variable-width codes when a match is found. It adds new sequences to the dictionary and increases the code width as the dictionary grows, and emits a CLEAR code and reset once the dictionary is full. The resulting codes are packed into the output bitstream.

Testing Pack

Testing Pack() proved to be a lot trickier than Unpack(). Since the engine used in Tomb Raider VI essentially does a complete world state snapshot, saving multiple times in a row, even without changing anything in-game, will still produce a completely different buffer, and thus a different compression stream.

Since I had to have an identical decompressed input stream every time I saved, I used a script to dump a decompressed buffer from the game. That became my testing dataset. I then set a breakpoint on Pack(). I would then save in-game, and then immediately inject the decompressed buffer into the game's memory to produce the same compressed output. I could then feed the same input into my recreation of Pack() and diff the results.

This made it possible to identify the exact offset where my compressed output first diverged from the game's. The early Python script I had was already producing a matching prefix, so debugging here mainly involved a process of making small adjustments in the control flow to get it to match the game's output further.

One of the first fixes was the timing of the variable-width code transition. The initial implementation in my script incremented the dictionary code before checking if the code width needed to increase:

PYTHON 

dictionary[hash_index] = (combined_code << 12) | next_code
next_code += 1

if next_code > max_code and code_width < MAX_BITS:
    code_width += 1
    max_code = (1 << code_width) - 1

Moving the width transition before the dictionary insertion more closely reproduced the original function's control flow:

PYTHON 

if next_code > max_code and code_width < MAX_BITS:
    code_width += 1
    max_code = (1 << code_width) - 1

dictionary[hash_index] = (combined_code << 12) | next_code
next_code += 1

That small change extended the matching compressed prefix from approximately 0x123 to 0x1C1 bytes. The remaining differences were considerably harder to isolate.

Differential Testing

At this point, I had ported my reimplementation of Pack() and Unpack() into C# so I could integrate it with my editor. My Unpack() implementation appeared to be matching the game's output every time, while my Pack() implementation was consistently diverging in the 0x900 to 0xA00 range every time.

Eventually I changed my methodology and created an entire pipeline to test end-to-end compression and decompression. There are 35 levels in the game, each of varying buffer sizes due to entity counts, map sizes, etc. So in my pipeline, I had a dataset of 35 compressed savegame buffers produced organically by the game.

The test pipeline took each buffer, fed it into my Unpack() implementation, then took the resulting decompressed buffer and fed that into my Pack() implementation, and printed out a small diff info block about the divergence. The results looked like this:

OUTPUT

=========================================================================
[ERROR] Mismatch detected at 0x941 of compressed buffer
 - Expected byte:  0x13

Across almost every dataset, the first divergence was occuring in that same 0x900 and 0xA00 range. Since the buffers varied considerably in decompressed size, this strongly indicated that there was a subtle condition in Pack() that I wasn't accurately handling.

Pseudocode vs. Assembly

While the testing pipeline was a great idea to evaluate the draft implementations of Pack(), I was unfortunately stuck here for quite some time, still getting divergence in the 0x900 to 0xA00 range. The game was simply not accepting the compressed output that my editor was giving.

This is when I decided to change my debugging methodology. At this point, I had been relying almost entirely on Ghidra's C pseudocode as the ground truth for Pack(). Clearly there was something else going on that I was missing. I added tons of logging on my Pack() implementation, specifically around the divergence point, which in the specific dataset I was using, was at 0x99F. I logged the following:

  • Every code written, including its value, width, bit buffer, bit count, bit position, and output offset
  • Every output byte
  • Every code-width increase
  • Every dictionary insertion, including the hash index, next code, and combined code
  • Every dictionary-full / CLEAR event and the resulting reset position

I set a conditional breakpoint in the game's Pack() that would trigger once its output bit position reached the divergence point. I then dumped the game's LZW hash table and compared it against a raw dump of the 0x1400-entry table from my implementation.

I expected to find a small difference at the end of the tables. Instead, I found that the two dumps were very different. This lead me to believe that the incorrect byte at 0x99F was a result of a divergence that occurred much earlier. At this point, since I had narrowed down the problem to dictionary lookup and insertion logic, I decided to scrutinize the assembly code rather than relying on Ghidra's C pseudocode.

Reading the assembly made the problem much clearer. The problem with my implementation was that I was confusing the value used as dictionary key with the calculation used to select its hash-table slot. I was also resolving collisions using linear probing, while the game's Pack() calculated a probe step from the initial hash index. Accounting for this is what led to an implementation that produced compressed output that the game finally accepted. So now I had a fully working end-to-end compression/decompression codec that the game accepted... this was enough to publish a working editor.

The Remaining Edge Cases

At this point, I had a reimplementation of Unpack() that appeared to produce identical output to the game, and a reimplementation of Pack() that was close enough to the game's. It was still diverging in the 0x900 to 0xA00 range most of the time. After a long break from working on this particular problem, I eventually returned to fix the remaining edge cases.

The result of the edge case in Pack() was that it would corrupt the buffer after 2-3 consecutive cycles of saving. Returning to the ASM to debug this issue, I accidentally found out that there was actually a subtle edge case in my Unpack() implementation as well.

My implementation was reading the compressed bitstream in 32-bit chunks using C#'s BitConverter.ToUInt32(). This was leading to out-of-bounds reads, which ended up stopping decompression whenever less than four bytes remained in the compressed buffer.

000bda1f  AND     EBX,0x1F

I fixed the edge case by replacing the strict 32-bit reads with zero-padded 32-bit reads, allowing Unpack() to safely decode the remaining bits at the end of the compressed buffer. Now my reimplementation of Unpack() was effectively 1:1 with the game's.

So, with that fixed, all that remained was Pack(), which was still diverging in the same 0x900 to 0xA00 range. I returned to my testing pipeline, and added numerous amounts of debug statements to narrow down which part of the ASM to investigate.

Eventually, I narrowed down the final difference to the dictionary collision logic. In the ASM, there were actually two subtly different comparisons. When checking the initial hash slot, the game applied a signed correction to the dictionary entry before comparing its key. While my version of Pack() reproduced this behavior, it over-corrected by reusing it for every collision probe as well.

The assembly revealed that collision probes used a normal unsigned right shift instead. I changed my implementation so that the initial hash-slot lookup and collision-probing loop were handled separately. With that final change, my reimplementation of Pack() finally produced byte-for-byte identical output to the game's.

C# 

if (dictionary[hashIndex] != 0)
{
    // Initial hash-slot comparison uses signed correction
    int entry = unchecked((int)dictionary[hashIndex]);
    int adjusted = entry + ((entry >> 31) & 0xFFF);

    if ((adjusted >> 12) == (int)combinedCode)
    {
        currentCode = (uint)(entry & 0xFFF);
        found = true;
    }
    else
    {
        // Collision probes use a normal unsigned comparison
        while (true)
        {
            int tempIndex = (int)hashIndex - (int)step;
            if (tempIndex < 0)
            {
                tempIndex += 0x13FF;
            }

            hashIndex = (uint)tempIndex;
            uint probeEntry = dictionary[hashIndex];

            if (probeEntry == 0)
            {
                break;
            }

            if ((probeEntry >> 12) == combinedCode)
            {
                currentCode = probeEntry & 0xFFF;
                found = true;
                break;
            }
        }
    }
}

Conclusion

The biggest lesson I learned in this project was how to treat the decompiler's pseudocode. I kept treating the C pseudocode as the ground truth when writing my reimplementations. By chance, this was almost enough for Unpack(), save for the final edge case.

In the case of Pack(), the C pseudocode was almost misleading in many ways. It wasn't until I started treating the ASM as the ground truth that I started to finally fix the remaining edge cases that seemed unsolvable.

Treat the C pseudocode as an abstraction. Treat the ASM as ground truth.
