Hacking the TP-Link TL-WR841N Router

Hardware Hacking / Embedded Linux

Gaining root shell access through UART, extracting the router's filesystem, and dumping its firmware directly via SPI flash.

10-03-2026

Introduction

The TP-Link TL-WR841N is an inexpensive wireless router and thus a useful target for experimenting with embedded Linux and hardware reverse engineering. My initial goal was to gain shell access through the router's exposed UART interface and determine how much of the system could be extracted and analyzed.

Do note that the router used for this project is hardware revision v14.6. Other revisions of the TL-WR841N may use different components, PCB layouts, or UART configurations. So the exact steps outlined in this page are not guaranteed to work.

Tools

This project required only a small collection of inexpensive hardware tools and standard software utilities. You can find pretty much all of the hardware on Amazon.

Hardware

  • CH340G USB-to-serial adapter
  • CH341A SPI programmer
  • Digital multimeter
  • Header pins and jumper wires
  • Soldering equipment

Software

  • PuTTY
  • Tftpd64
  • AsProgrammer
  • HxD

Finding the Serial UART Port

The router's PCB immediately exposes a UART header. The pads are conveniently labeled: GND, TX, RX, VCC. The pins are bare, so it is necessary to solder pins onto the header in order to get a stable connection.

Before connecting the serial USB adapter, I first verified that the UART's TX and VCC lines run at 3.3 volts using a multimeter. Connecting a serial device that runs at a higher voltage may destroy the router's PCB, the serial device, or both.

After soldering header pins to the board, I connected the serial USB adapter using GND-GND, TX-RX, and RX-TX. VCC is not neccessary for communication, so it was left disconnected.

Obtaining Shell Access

The UART interface operates at 115200 baud rate and standard serial settings. Once connected, the router exposes its boot output and an embedded Linux shell.

At this stage, the router was only able to send data, but it was not able to receive commands. As I learned, this is because TP-Link intentionally shorts the router's RX pin using a voltage-limiting resistor. Removing the resistor at R18 allowed the router to receive commands, establishing an interactive console.

Extracting the Filesystem

The router uses a heavily stripped-down version of Linux. As such, the BusyBox binary that it ships with is also heavily stripped down. It does however, contain TFTP, which makes it possible to move a less stripped-down BusyBox to the router. This is what allowed me to eventually archive the filesystem. Using the mount command, I observed a mostly read-only filesystem.

SHELL 

~ # mount
rootfs on / type rootfs (rw)
/dev/root on / type squashfs (ro,relatime)
proc on /proc type proc (rw,relatime)
ramfs on /var type ramfs (rw,relatime)
/sys on /sys type sysfs (rw,relatime)

Since /var is backed by writable RAM, it provides a convenient location for transferring and executing the more complete BusyBox binary. From there, directories can be archived and transferred to another machine using TFTP.

SHELL 

# Download BusyBox
cd var/tmp
tftp -g -r busybox-mipsel 192.168.0.100
chmod u+x busybox-mipsel
./busybox-mipsel

# Archive directory
./busybox-mipsel tar cvf /var/tmp/web.tar /web/

# Upload directory from BusyBox
cd var/tmp
./busybox-mipsel tar cvf /var/tmp/linuxrc.tar /linuxrc
tftp -p -r linuxrc.tar -l linuxrc.tar 192.168.0.100

Dumping the Firmware

After extracting the accessible filesystem, I moved on to obtaining a raw image of the router's flash storage. The board uses a cFeon 25QH32-series SPI flash chip.

Reading the chip in-circuit with an SOP clip was unreliable, as the clip would cause the router to intermittently power up. So I decided to desolder the flash chip and mount it directly on the CH341A programmer's SPI adapter.

With the chip isolated from the router, the programmer was then able to read the chip. Using AsProgrammer, I was able to rip the firmware from the chip onto a .BIN file. Inspecting the ripped .BIN file in a hex editor revealed the same strings observed in the bootloader.

The embedded string identifies the router's bootloader as U-Boot 1.1.3, built on August 16, 2022.

Running Custom Software

While the router has very limited resources and a mostly read-only filesystem, it is still capable of running simple terminal applications. I was able to get both Tetris and Snake running directly on the router.

Programs are best suited for the device when they are written in C or C++ and have no external runtime dependencies. As a demonstration, I cross-compiled a terminal implementation of Tetris and transferred the compiled binary to the router, and ran it.

The router uses a MIPS32 little-endian processor. Buildroot can be used to cross-compile C and C++ programs as statically linked MIPS32 little-endian binaries, avoiding dependencies that are unavailable on the router.

Once the Buildroot toolchain is configured, programs can be compiled and stripped with the following commands:

SHELL 

# Compile C binary
mipsel-buildroot-linux-uclibc-gcc -mabi=32 -mfp32 -EL -static -o program program.c

# Compile C++ binary
mipsel-buildroot-linux-uclibc-g++ -mabi=32 -mfp32 -EL -static -o program program.cpp

# Strip binary
mipsel-buildroot-linux-uclibc-strip program

Conclusion

This project began as a simple hardware reversing experiment to see if a root shell could be achieved via the UART port. Then the goal became a partial filesystem dump to see what TP-Link actually loaded the device with. Then the goal became to dump the firmware to see what it contained. Then finally, I just wanted to see if it was possible to play Tetris on the router... just for the hell of it.
