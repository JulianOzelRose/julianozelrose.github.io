Hacking the TP-Link Archer C60 to Play DOOM

Hardware Hacking / Embedded Linux

Porting DOOM to an embedded Linux router by gaining root shell access through UART, implementing terminal rendering, and cross-compiling for MIPS32 big-endian Linux.

10-17-2026

Introduction

My goal in this project was pretty simple: get a router to play DOOM. The cool thing about DOOM is that it is open source and has minimal dependencies. So if you have the right toolchain, you can compile DOOM to run on just about anything. Basically if it has a screen and a CPU, it can likely play DOOM.

A router, of course, has no screen (at least most models don't). But, modern routers typically run a stripped-down version of embedded Linux as their operating system, so they make good targets for this kind of project. My plan for achieving my goal started with obtaining a root shell via the UART port, modifying DOOM's source to display properly on a terminal, cross-compiling it for the router's architecture and environment, then making whatever adjustments were necessary to make it playable.

Hardware Reconnaissance

I ended up ordering a TP-Link Archer C60. The specific hardware revision and region are V3.0 (KR). Notice the exposed UART pads on the top left corner of the PCB. That was the main attack vector. Unfortunately, merely having exposed UART pads doesn't guarantee a shell. Sometimes it's read-only, sometimes RX is disconnected, sometimes there's authentication, sometimes it's disabled on the firmware level, etc...

Usually, if it's a later model, it's going to be some combination of those protective measures. It can become a real pain to deal with if you just want a shell so you can mess around. But if you want an easy shell, you basically have to play revision lottery and pray that the one you ordered isn't heavily locked down.

So after I identified the UART pads, I soldered some header pins onto them. The router's UART pins were not labeled, so I had to figure out which pin was which. UART layout is usually VCC, GND, RX, TX.

Using continuity mode on my multimeter, I located GND by using the metal pad in the middle of the PCB as one point, and testing it against each pin until I got a chirp. Then I knew which pin was GND.

With GND known, I was then able to test the voltages of the other pins. One was giving a steady 3.3v. I concluded that was likely VCC. Another one was giving ~2V, so I figured that was TX. The last one was dead silent, so I figured it must be RX.

The layout of the router's UART pins (starting from the top) is:

Pin Function
Pin 1 TX
Pin 2 RX
Pin 3 GND
Pin 4 VCC

Obtaining Root Access

At this point, I have an exposed UART, which I know runs at 3.3v, and I'm reasonably confident of the pin layout. So I connect it to my TTL adapter, plug it into my PC and fire up PuTTy. I used a baud rate of 115200, 8N1, no flow control. Now to just see if I guessed right and won the revision lottery...

... And we're dropped directly into a root shell. Also, the router can receive commands, so it's a bidirectional terminal. Jackpot. I started by running a few commands to check the router's CPU and memory to see how feasible running DOOM on it would be.

Component Specification
SoC Qualcomm Atheros QCA956X
CPU MIPS 74Kc V5.0 (Single-Core)
Architecture MIPS32 Big-Endian
Operating System Linux 3.3.8
Total RAM 63.2 MB
Free RAM 25.2 MB
Temporary Storage /tmp (31.7 MB tmpfs)
Swap None

So we're looking at a MIPS32 (BE) router with about 32 MB of maximum writable storage, and a very old version of Linux. Given that DOOM's main binary is about 700 KB, and the WAD file is about 12 MB, this is actually quite promising.

Also, the router's BusyBox has tftp, so we can transfer files to and from the router.

Cross-Compilation for MIPS32

I knew I would have to modify the game somehow to be able to display properly on a terminal. But first, I had to figure out how to cross-compile it. Since the router uses embedded Linux, I used Buildroot to generate my cross-compilation toolchain. I used the following compilation settings for Buildroot:

Setting Value
Target Architecture MIPS (Big Endian)
CPU Architecture MIPS32 Release 2
CPU Model MIPS 74Kc
ABI O32 (32-bit)
Floating Point Software (Soft-Float)
Toolchain Type Buildroot Internal
C Library uClibc-ng
GCC Version 14.3.0
Linux Kernel Headers 3.3.x
C++ Support Enabled
Library Linkage Shared and Static
DOOM Linkage Static
Optimization -O2

Based on the settings alone, it should work on this MIPS router in theory. But I was afraid the old Linux kernel headers version might cause the compiler to throw errors. Fortunately, it compiled smoothly to MIPS32 BE. No errors.

Porting DOOM to the Terminal

Before moving anything to the router, I had to figure out the best way to port DOOM so that it was playable on a terminal. I started with doomgeneric as a base. For my first build, I modified it to use ANSI truecolor, Unicode half-blocks, and framebuffer downsampling for proper terminal display.

I tested it out a bit in VirtualBox. I thought it basically looked like a super low-resolution DOOM. But it did run, and it was playable. I did have to modify it a bit further so that the keys were usable on the terminal, switching to WASD instead of arrow keys for movement.

Deployment and the UART Bottleneck

Once I had my ANSI build of DOOM working on my VirtualBox terminal, I thought it was a good enough proof of concept to begin testing it out on the router. Basic deployment consisted of just uploading the DOOM binary and the WAD file to the /tmp directory using the router's built-in TFTP client.

SHELL 
# Download files from Windows Tftpd32 server
cd /tmp
tftp -g -r doomgeneric-ansi-mipsbe 192.168.0.192
tftp -g -r DOOM.WAD 192.168.0.192

# Make executables runnable
chmod +x doomgeneric-ansi-mipsbe

# Launch
./doomgeneric-ansi-mipsbe -iwad DOOM.WAD

It did actually execute on the router, but it felt a bit like a slideshow. It was pretty much unplayable via UART. At 115200 baud rate 8N1, maximum throughput should be around 12 KB/s. So the slideshow effect is the result of a bandwidth problem, not a CPU/resource problem.

Instead of using the UART as the primary interface to play the game, I thought spinning up a Telnet server on the router then connecting from my PC via terminal would be much smoother. The router's BusyBox lacked the telnetd server function, so I had to go back to my Buildroot toolchain to compile a new BusyBox for MIPS32 BE. This ended up working much better than trying to play it through the UART.

Results

Shortly after getting my ANSI build running smoothly on the router, I discovered that there was in fact already a solution to running DOOM properly on terminal display: SSHDOOM. I didn't really have to modify it much other than just change the movement keys to WASD. I played it through Telnet via Windows Terminal, and it rendered beautifully.

The framerate isn't super high, and you're limited to one keypress at a time, but it's definitely playable. Since it's in a terminal, there is no audio, but the save/load feature actually works.

I also ended up switching to the shareware version of DOOM's WAD file (DOOM1.WAD). Since it was 4 MB instead of the stock DOOM's 12 MB WAD file, it ended up freeing some resources, making the gameplay a bit smoother. Below is the full set of commands I ended up using:

SHELL 
# Download files from Windows Tftpd32 server
cd /tmp
tftp -g -r busybox-mipsbe 192.168.0.192
tftp -g -r doomsixel-mipsbe 192.168.0.192
tftp -g -r DOOM1.WAD 192.168.0.192

# Make executables runnable
chmod +x busybox-mipsbe doomsixel-mipsbe

# Start Telnet server
./busybox-mipsbe telnetd -p 2323 -l /bin/sh

# Windows Terminal (PowerShell)
py router-telnet.py

# Launch Sixel DOOM (from Python Telnet session)
cd /tmp
./doomsixel-mipsbe -iwad DOOM1.WAD

# NOTE: Windows built-in Telnet does not render Sixel correctly
# Python client forwards Sixel directly to Windows Terminal

Conclusion

This project was pretty fun and I'd highly recommend it if you're trying to explore hardware reverse engineering or embedded systems. With 64 MB of RAM and only 32 MB being actually writeable, I think DOOM is probably about the most intense game that this router could handle.

I think it would have been cool to take the project a few steps further and maybe mod a screen and basic controller or keypad onto the router. That way you could play DOOM without having to use Telnet or another device to help display the output.
