Hacking the TP-Link Archer C64 Router

Hardware Hacking / Firmware Reverse Engineering

Investigating an authentication-locked UART console, extracting firmware through SPI flash, and reverse engineering the firmware to recover the router's login credentials.

10-18-2026

Introduction

My apartment had the Internet upgraded recently. The techs who came over installed a new router that was specific to the new service installed. Since I had bought the old router myself, I ended up with an extra router I no longer needed. So I decided to take it apart and see what security measures it had. I initially planned on stopping at a shell, but it just became too interesting to stop.

Hardware Reconnaissance

The router I had was the TP-Link Archer C64. The hardware revision and region are V1.0 (KR). Removing the housing was a bit difficult. I had to use a spudger. Upon opening it, I looked for the UART port. The UART pin layout and voltage are both labeled by the board. The pads are blocked with solder.

So there are two options: (1) remove the solder and add header pins, or (2) solder the wires directly to the existing solder. I decided to go with the first one. I think it took me like 30 minutes to properly clear the solder from the UART pads. I used a desoldering wick and a desolder pump.

After soldering header pins to the now-cleared pads, I connected my adapter, opened PuTTy, and booted up the router. I didn't have a logic analyzer and the UART runs at a pretty uncommon baud rate, so it took me a bit of trial and error to figure out what it was. But the proper settings for this model and revision are 117000 baud, 8N1, no flow control.

Auth-Locked Console

Fortunately, the RX pin was not disabled, so I had an interactive console and could send commands to the router. However, the router's console was locked with a password. After 5 attempts, the router makes you wait 30 minutes to try again.

I tried some easy/common passwords like "admin", "password", "12345", etc. No luck. I was considering stopping here, but then I thought this could be an interesting puzzle. The authentication routine is surely stored in the firmware. So if I can extract it, it might just become a crackme challenge in the form of firmware.

Firmware Extraction

After measuring the router's flash chip's VCC pin at 3.3V, I connected my SPI flash programmer to it. I decided to try to do an in-circuit read with the clips. This tends to be pretty hit-or-miss... sometimes you end up powering the SoC and it doesn't work.

If that ends up being the case, you either have to temporarily lift the chip's power pin from the board and then extract the firmware, or you have to completely desolder the chip from the PCB, solder it onto the SPI programmer, extract, and then solder it back to the PCB.

Fortunately in my case, none of that ended up being necessary. The SPI programmer was able to do an in-circuit read and I got a clean firmware dump on the first try.

Firmware Unpacking & Reversing

Instead of throwing the firmware in Ghidra right away, I decided to run it through Binwalk on my VirtualBox Ubuntu setup. I found that there were two separate packed U-Boot images, both compressed with LZMA. After decompressing both images, I tried searching them for the authentication-related strings that I saw in the terminal. It was a dead end, so I decided to take another look at the UART boot logs.

This portion of the boot log shows up after the second U-Boot executes. This line in particular is very interesting: imgFileEnc=0x30034da8, offset=0xfda8, len=0x1847bc. These are the offsets of the main image running that contains the authentication routines. So I extracted the payload from 0x34DA8 to 0x1847BC from the main firmware image.

The extracted payload began with an LZMA header, so I decompressed it, then searched for auth-related strings.

OUTPUT 
0x40D7B1  Console logout success
0x40D8B9  console exit.
0x40DA1C  Password:
0x40DA63  Console login success.
0x40DA7B  Incorrect passwords(%d/%d).

So, we have the password prompt string, the incorrect password string, and the correct password string. I threw the decompressed payload into Ghidra to begin searching for the authentication routine, hoping to eventually find something like a strcmp and eventually the actual password string.

Ghidra wasn't able to correctly map the strings to XREFs, so some pointer math was needed to locate the auth subroutine based on the string table. But this is the authentication block. DAT_00319b80 gives the password pointer 0x4063406C. Subtracting the firmware image base address of 0x40205000 gives the file offset at 0x42F06C, where the expected password is stored in plaintext:

Result

And we're in. Once past the auth, you can use help for a list of commands. They're mostly debugging commands, as this is TP-Link's custom TPOS. If you want to mess with the router further and try to port stuff onto it, then the most useful one is probably tftp.

I didn't try porting anything to it, but it actually might not be a bad target. It does have a 1.2 GHz CPU, which is pretty fast for a router. However, it only has 64 MB of RAM. The architecture is ARM32 (LE).

Conclusion

I didn't really think a project would come out of this. I just wanted to look at the router's PCB, gain access to the UART, see if a shell was possible, and move on. But it quickly turned into a firmware RE-based crackme, so it was just too interesting to pass up.

It's kind of amusing to see the lengths that these companies go through to make sure you don't achieve a shell on their routers:

  • Disconnecting the PCB line for UART RX
  • Shorting RX with a resistor
  • Disabling RX via the firmware
  • Adding an authentication wall
  • Some combination of the above

If I didn't know any better, with this kind of layered security, I'd assume the nuclear launch codes are stored somewhere on these things. It's almost anticlimactic when you bypass all that hardware and software-level security only to find out they're protecting some basic RTOS that doesn't really do much anyway.

At this rate, they might as well just start physically booby-trapping the PCB so you can't access their precious RTOS.
