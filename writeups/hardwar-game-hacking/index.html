Understanding Pointers Through Game Hacking

Game Hacking / Reverse Engineering

Exploring pointers and memory addresses through game hacking, using a custom trainer written for the cyberpunk PC game HardWar as a practical example.

10-12-2026

Introduction

When I took my first computer science courses at university, I remember having trouble wrapping my mind around the concept of a pointer. Apparently this is a common problem among computer science students. I eventually understood that a pointer is essentially a variable that holds a memory address. The pointer itself is just a number representing that address. Dereference it, and you get the value it points to. It's supposed to be simple, but without a concrete example of a pointer being manipulated somehow, it might seem a bit abstract.

A couple years later, I started experimenting with game hacking and reverse engineering. I fell in love with it quickly. I wrote my first trainer for an old game I used to play a lot, HardWar. Since pointers are crucial concepts in reverse engineering, I came to understand pointers at a much more in-depth level. More than that, I think a hands-on demonstrative way of learning pointers suits visual learners a lot better.

I'll summarize the basics of this game so the terminology is not lost. In a nutshell, this game takes place on Saturn's moon, Titan. It's a very cyberpunk/dystopian setting. The moon's craters are cities. Players (or "pilots") fly around in ships called moths, which can hover and are equipped with weapons and targeting systems. Buildings are called "hangars", and there is a fully-functioning economy in the game. It has a campaign and a multiplayer component as well.

Where Pointers Come In

When you build your first trainer, the first thing you realize about pointers is the difference between static and dynamic pointers. A static pointer is essentially a stable pointer that can be found at the same offset relative to the game's executable or another loaded module every time you open the game. A dynamic pointer is one that is allocated at runtime, and its exact address will change every time you open the game.

So, in order to build a working trainer, you must understand this distinction, and you must be able to use static pointers to find dynamically-allocated memory addresses. As an example, you might start by finding the dynamic memory address of your player object. But, because you need a stable reference to that pointer, you'd have to find a static pointer that points to it next.

It is also important to understand how memory offsets work. An offset is the distance from a base memory address, usually expressed in hexadecimal form. For example, if an object starts at address 0x1000 and a value is stored at offset 0x30 of that structure, then that value's absolute address would be 0x1030.

Pointer Chains

When I wrote my first trainer, I thought an insta-kill feature would be pretty funny. You target an enemy pilot, and their moth instantly explodes. I had some other ideas for what I wanted to implement. I wanted a trainer that had:

  • Insta-kill
  • Speedhack
  • Invincibility
  • Infinite cash
  • Stall negation

Almost all of these require a chain of pointers to be resolved dynamically, mostly through chains of linked structures and sub-structures. The simplest chain in this case would be player cash. It's directly on the player structure, so the pointer chain would be:

player → cash

Insta-kill is the most interesting one because it involves the longest chain of pointer resolutions in order to work. We basically have to, in order, resolve:

  • Player pointer
  • Player location (moth)
  • Player moth's current target (enemy moth)
  • Enemy moth's damage value

So, visualized, the full sequence is:

player → location → target → damage

To access these values, the trainer needs to follow a series of pointers until it reaches the target memory address. I used a helper function that takes a base address and a list of offsets, then resolves the chain.

C++ 
uintptr_t FindDmaAddress(HANDLE hProc, uintptr_t ptr, std::vector<unsigned int> offsets)
{
    uintptr_t address = ptr;

    for (unsigned int i = 0; i < offsets.size(); i++)
    {
        ReadProcessMemory(hProc, (BYTE*)address, &address, sizeof(address), 0);
        address += offsets[i];
    }

    return address;
}

Pointer resolution function adapted from a Guided Hacking tutorial

This function starts with the base address passed in, iterates through the list of offsets, and dereferences the pointer at each step before adding the corresponding offset. Once all offsets have been processed, it returns the final memory address.

Resolving Pointer Chains

So the trainer I wrote starts with a stable module-relative pointer: HardwarW.exe + 0x11D9AC. This holds a pointer to the player object. All the other pointer chains are derived from this. The code blocks below show how the pointer chains are resolved for each of the cheat features. The reading and writing of the values are performed in a loop, but the loop has been omitted for simplicity. Note that ReadProcessMemory() and WriteProcessMemory() come from the Windows API.

C++ 
// Cash is accessed through a single pointer dereference and field offset
std::vector<unsigned int> cashOffset = {0x03C};

uintptr_t cashAddress = FindDmaAddress(hProcess, dynamicPtrBaseAddress, cashOffset);

ReadProcessMemory(hProcess, (BYTE*)cashAddress, &cash, sizeof(cash), nullptr);

// Force cash to max value
if ((cash < MAX_CASH) && (playerAddress != NULL))
{
    WriteProcessMemory(hProcess, (BYTE*)cashAddress, &MAX_CASH, sizeof(MAX_CASH), nullptr);
}

So, that's how the player pointer is dereferenced, the cash address is resolved, and the value is modified. We use a conditional to ensure that the cash stays at a certain value. Since this requires only one pointer dereference, it's the simplest example.

C++ 
// Thrust is accessed through two pointer dereferences and a field offset
std::vector<unsigned int> thrustOffsets = {0x030, 0x438};

uintptr_t thrustAddress = FindDmaAddress(hProcess, dynamicPtrBaseAddress, thrustOffsets);

ReadProcessMemory(hProcess, (BYTE*)thrustAddress, &thrust, sizeof(thrust), nullptr);

// Increase thrust to 6x maximum
DWORD newThrust = MAX_THRUST * 6;

// Apply speedhack when in flight
if ((bSpeedHack) && (mothStatus != IN_HANGAR))
{
    WriteProcessMemory(hProcess, (BYTE*)thrustAddress, &newThrust, sizeof(newThrust), nullptr);
}

The speedhack here involves the first multi-level pointer chain. Starting from the player base pointer, it adds 0x30 to the player's location pointer (in this case, a moth), then dereferences it. It then adds 0x438 to access the moth's thrust value, and increases it to a value much higher than what the game permits under normal circumstances.

C++ 
// Target structure damage is accessed through three pointer dereferences and a field offset
std::vector<unsigned int> targetStructureDmgOffsets = {0x030, 0x1F0, 0x29C};

uintptr_t targetStructureDmgAddress = FindDmaAddress(hProcess, dynamicPtrBaseAddress, targetStructureDmgOffsets);

ReadProcessMemory(hProcess, (BYTE*)targetStructureDmgAddress, &targetStructureDmg, sizeof(targetStructureDmg), nullptr);

// Instantly destroy the targeted moth
if ((bInstakill) && (targetType == TYPE_MOTH) && (targetStructureDmg != MAX_DMG) && (playerStatus == IN_MOTH) && (targetStatus != IN_HANGAR))
{
    WriteProcessMemory(hProcess, (BYTE*)targetStructureDmgAddress, &MAX_DMG, sizeof(MAX_DMG), nullptr);
}

To achieve insta-kill, the trainer starts from the player base pointer, and then adds 0x30 to locate the player's location (again, a moth). It then follows the pointer at offset 0x1F0 to the current target (enemy moth). Finally, it adds 0x29C to locate that moth entity's damage field, and sets it to the maximum value. This makes the targeted moth explode instantly.

Putting it All Together

To ground all of the reverse engineering concepts to the actual code that it originated from, it is useful to visualize the game's structures as they may have appeared in the original code.

C++ 
struct Pilot
{
    uint8_t status;     // +0x02C
    uint32_t location;  // +0x030
    int32_t cash;       // +0x03C
};

struct Moth
{
    uint32_t target;    // +0x1F0
    uint32_t damage;    // +0x29C
    uint32_t thrust;    // +0x438
};

Now, this is a rough and simplified abstraction. But basically, in the game's original codebase, there may have been a Pilot struct and a Moth struct resembling these declarations. When the game gets compiled, references to the members of these structures are translated into instructions that access memory at specific offsets. In memory and disassembly, we see these members as relative offsets to the main structures.
